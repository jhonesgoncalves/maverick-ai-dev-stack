## Command details

### Tasks and delivery

`maverick init` interviews you, then writes `.maverick/config.json`. In a terminal it is a step-by-step wizard (↑↓ to move, space to toggle, `a` for all, enter to confirm, esc to go back or cancel) that asks the project name, what the project does and for whom, which AI agents work on it as a checkbox list (Claude Code, Codex, Cursor, GitHub Copilot, Gemini CLI, Windsurf, Kiro, OpenCode; the ones found in the repository or on the machine come pre-checked), the docs language (default from `LANG`, so `pt_BR.UTF-8` gives `pt-BR`), the code language (default `en`), the default workflow and which detected verification commands to use, then shows a summary before writing anything. Every question has a flag for scripts: `--name`, `--description`, `--agents claude,kiro,codex`, `--docs-language`, `--code-language`, `--workflow standard|strict`, `--verify "npm test; npm run lint"`; `--yes` accepts the suggestions. It installs the eight flow skills once into `.agents/skills/` and makes each chosen tool's skills folder a symlink to it (`.claude/skills → ../.agents/skills`), writes `AGENTS.md` from the answers when it is missing, and links `CLAUDE.md` and `GEMINI.md` to it for the tools that do not read `AGENTS.md`. Existing files are never replaced. `--no-skills` and `--no-instructions` skip those steps. On an initialized project, `maverick init --agents gemini` adds agents without asking again. `maverick language` (alias `lang`) shows the languages; `maverick language pt-BR en` sets docs and code, `--docs <code>` or `--code <code>` sets one, and `--json` prints them. `maverick new "<idea>"` (aliases `open`, `start`) derives a slug from the idea (`--slug` to choose), writes `TASK.json`, grounds the idea in the code (ranked relevant files with reasons, nearby tests, entry points, shared modules, verification commands) and, in a terminal, opens your AI coding agent with the eight flow skills installed, prompted with the skill for the task's stage (`--agent` to choose; `--strict` for the strict workflow; `--no-launch` to only create the task). `maverick new <slug>` resumes a task in the agent with the skill for its stage: planning uses `maverick-new`, build `maverick-build`, verify, security and review `maverick-review`, and PR `maverick-ship`. `maverick new` with no idea opens the agent, which asks what to build. Without a terminal it only creates the task. `maverick instructions <task> [prd|techspec|tasks] [--json]` returns what a skill needs: the idea, current stage, required headings, earlier artifacts, grounding and findings, plus `skill`, `language` (docs, code, rule, keywords) and `tasks` (total, done, ready with paths, in progress). `maverick generate <task> [stage] --agent <provider> [--answers "…"]` runs the stage skills headlessly with a trusted, read-only agent, then writes and strictly validates each artifact, retrying once with the failures. `validate <task> [--stage prd|techspec|tasks] [--strict]` checks headings, unique acceptance-criteria ids, requirement scenarios, that referenced paths exist, that the Test Plan covers every criterion, and that every criterion is covered by a task. `status` shows each task's stage and names the skill for its next step. `map`, `packet`, `run`, `verify`, `checkpoint`, `impact`, `guard`, `security`, `deps`, `review --diff`, `pr`, `handoff`, and `readiness` turn those artifacts into an auditable delivery workflow. See [From idea to tasks](/guide/planning).

### Repository configuration

`policy init|show|check`, `adapter list|install`, and `ci github <task>` provide repository-level configuration, agent instructions, and an optional GitHub Actions task gate. Most operational commands accept `--json` for automation.

### Stack and configuration

`stack [--json]` reports detected languages, frameworks, package managers, task runners, subprojects, and the exact commands `verify` will run for JavaScript/TypeScript, Python, Go, Rust, Java/Kotlin, .NET, Ruby, PHP, Elixir, Dart/Flutter, and Swift projects. `config show|validate|path` inspects the layered configuration (defaults, `~/.maverick/config.json`, project). `doctor` also checks that each detected toolchain binary is installed. `help` is generated from the same command registry used for routing and the Lens CLI explorer.

### Capabilities

`catalog [search <text>|show <name>|validate]`, `add <capability...> [--to <tools>] [--dry-run] [--yes] [--force] [--allow-exec]`, `remove <capability...>`, `installed`, and `sync` manage skills, agents, commands, and MCP servers across Claude Code, Codex, Cursor, GitHub Copilot, Gemini CLI, Windsurf, Kiro, and OpenCode. With `capabilities.layout: "linked"` (the default, except on Windows) each capability is written once to `.agents/` and each tool's skills folder is a symlink to `.agents/skills` (`.claude/skills → ../.agents/skills`), so every skill, including ones you add, is shared by all agents; skills already in a tool's folder are moved into `.agents/skills` first, and a name that differs between tools stops the install; `maverick sync` installs the new catalog version of every capability that changed (shown as `UPDATE` lines and applied only with `--yes` or a confirmation; `--no-update` only restores drifted files), adds flow skills that are new in a release wherever `maverick-new` is installed, and converts an existing install when the layout changes; `maverick sync <task>` converts a task written by an older Maverick to the current format (checklists for criteria, steps and tests, and `_tasks.md` as a checklist of the tasks), with `--dry-run` to preview; agents, commands and MCP servers whose format differs per tool are rendered for each one. `"copy"` writes each tool its own files. Installs are planned before anything is written, recorded in `.maverick/capabilities.lock.json` with content hashes, and never overwrite files or JSON keys Maverick does not own unless `--force` is passed.

### Flows and subtasks

`flow list|show|validate|run <flow> <task> [--reset] [--auto-approve]|status <task>|approve <flow> <task> <gate>|auto-approve [<flow> on|off]` runs contract-driven flows: typed gates (`check`, `maverick`, `command`, `artifact`, `approval`), an iteration cap, and a no-progress window, ending in `done`, `revise`, `awaiting-approval`, `stalled`, or `exhausted` (only `done` exits zero). `flow approve` (`--reject --reason "..."` to request changes) checks the matching box in the gate's file, such as `- [x] approve` in `REVIEW.md`, and decides a run that was only waiting on it right away. `--auto-approve` runs without waiting for a human: once every blocking check passes, pending approval gates are approved and marked as auto-approved; `flow auto-approve <flow> on` makes that the default for a flow in `.maverick/config.json`. `subtask add|list|next|set|validate <task>` manages an acyclic subtask graph whose dependencies are enforced when work starts or finishes.

### Headless agents

`agent list|trust <provider>|untrust <provider>|run <task>|runs <task>` runs Claude Code, Codex, Cursor CLI, Gemini CLI, or custom CLIs headlessly. `agent run` accepts `--subtask <id|next>`, `--prompt`, `--provider`, `--model`, `--permission read-only|edit|full`, `--timeout <minutes>`, and `--dry-run`; permissions never exceed `runtime.maxPermission`, and only providers in `runtime.trusted` run. `flow run <flow> <task> --agent [provider]` lets the agent fix blocking issues between runs until the flow is done, stalled, exhausted, or the agent asks for a human.

### Project intelligence

`graph [--json] [--format mermaid|dot] [--depth <n>]` reports the resolved import graph across languages (cycles, hubs, fan-in, instability, and a health score with its formula). `impact <path>` lists transitive dependents and the tests to run, falling back to text references for non-source files. `hotspots [--since <git date>] [--limit <n>]` ranks files by churn and dependents. `mcp` starts a read-only Model Context Protocol server over stdio; its `ground_change` tool returns the same grounding as `maverick new`.

`routes [--kind http|page|graphql|rpc|event|job|websocket] [--method <verb>] [--grep <text>] [--json]` lists entry points in any stack—decorators and annotations, router calls, file-system routing and OpenAPI, GraphQL or protobuf contracts—with guards, duplicates, contract drift and write routes without a guard. `coupling [--json]` reports components with afferent and efferent coupling, instability, abstractness and distance from the main sequence, component cycles, Stable Dependencies Principle violations and configured boundary rules. `audit [--severity high|medium|low] [--category <name>] [--fail-on high|medium|low] [--json]` ranks every architecture finding with its evidence; `--fail-on` makes it a CI gate. `impact <path>` also lists the entry points served by the affected files. See the [Devtools guide](/guide/devtools).
